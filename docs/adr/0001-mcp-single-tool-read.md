# ADR 0001：MCP 只暴露一个工具 `read`

- 状态：已接受（2026-11-28）
- 相关：`GLOSSARY.md`、`docs/PLAN.md` §7 / §9

## 背景

xdoc 给 Agent 的入口是 MCP 工具。第一版只暴露了 `read`，后来陆续要加的能力有：
先看结构（大纲）、按页取正文、只找关键词、读整个目录、限制 token 预算、继续读剩下的部分。

每加一种能力就多一个工具（`outline` / `grep` / `read_dir` / `continue`）是很自然的想法。
但 Agent 侧的真实约束是：**工具列表本身就是要占上下文的**，而且 Agent 需要先猜「该用哪个工具、
怎么传参」，猜错就得试错。

## 决策

**MCP 侧永远只暴露一个工具 `read`。** 所有读取能力都做成 `read` 的参数：

| 能力 | 参数 |
|---|---|
| 换格式 | `format` |
| 控制体量 | `max_tokens` |
| 接着读 | `cursor` |
| 只取某几页 | `pages` |
| 只要结构 | `outline` |
| 只找关键词 | `grep` / `grep_regex` / `grep_context` / `grep_limit` |
| 感知开关 | `ocr` / `asr` / `asr_model` / `tables` / `images` |
| 渲染 | `front_matter` |

CLI 侧**不做同样的收敛**：人用命令行时子命令更顺手，所以有 `xdoc read` 与 `xdoc grep`
两个子命令。但两者共用同一个读取入口，输出契约完全一致——CLI 只是同一个动作的另一种外壳。

## 后果

- **好处**：Agent 面对的接口面永远是「一个工具 + 一堆自解释的参数」。
  每个参数在 schema 里都带说明，枚举值用类型约束直接暴露，Agent 不需要试错就知道怎么传。
- **代价**：参数会变多（现在 16 个）。所以每个参数必须有 `description`，
  并且要在工具描述里给出**推荐调用顺序**（先看结构 → 再找关键词 → 再取页 → 再续读），
  否则 Agent 面对一长串参数仍会犹豫。
- **代价**：互斥的组合必须显式报错而不是静默取其一。例如大纲与检索同时使用会直接报错。
- **后续**：若将来某个能力的参数数量压不住了（例如要按语义过滤），应先想清楚能不能拆成
  「先定位、后取回」两步，而不是先加工具。
